# Redmi K50 Ultra 渲染线程与 GPU 开销，第二轮（2026-10-17）

English: [2026-10-17-perf-round2.md](2026-10-17-perf-round2.md)

接着 [2026-10-17-frame-overlap.zh-CN.md](2026-10-17-frame-overlap.zh-CN.md) 往下做，以那篇的帧重叠（PR #9）为起点。11:30–16:25（新西兰夏令时）在 Redmi K50 Ultra（Adreno 730、Vulkan 1.1、Android 15）上测。构建为 `android/linux-build`，引擎改动在分支 `android/perf-round2`。
- **场景：** 同前的营地场景：冷启动，对已存的女巫点「开始」，取最后四个 60 帧的 `NVN PERF v=1` 窗口。
- **标记：** 每一行都开着 `gfx-defer-events=2` 和 `gfx-present-overlap=1`。
- **温度：** 电池超过约 36 °C 时，就把手机放回桌面晾 30 分钟。下面每组对比都在相近温度下测，每行注明电池温度。
- **工具：** 手机上的 simpleperf（`simpleperf record --app`，cpu-clock，DWARF 调用栈）、引擎自带的逐通道 GPU 计时（`gfx-pass-profile`），以及途中新加的计数（见下）。

## 结果

| 步骤 | 电池 °C | 营地帧率 | CPU 提交 ms | GPU ms |
|---|---|---|---|---|
| 起点：帧重叠（PR #9） | 32 | 19.7 | 41.6 | 41.6 |
| 计时作用域每 8 帧计一帧；命令区间缓存 | 35 | 21.2 | 37.5 | 42.0 |
| 彩色图像不带 `MUTABLE_FORMAT`（保住 UBWC） | 33 | 23.8 | 33.7 | 36.2 |
| 帧缓冲跨帧保留；每槽一个命令池；少一些堆分配 | 27 | 24.3–24.7 | 32.1 | 36.6 |
| 纹素缓冲的描述符集进入备忘 | 31 | 25.6–26.1 | 27.4 | 36.8 |
| 每段连续绘制一个遮挡查询；快照与图像的前置缓存 | 28 | 32.3–33.1 | 22.7–23.3 | 25.2 |
| 一级管线查找；每次绘制的计数改为宽松原子；快照节点复用 | 28 | 35.5 | 20.6 | 25.5 |
| 存储写跟踪开启（走宿主的缺页钩子） | 30 | 36.3 | 19.5 | 25.3 |
| 打开着的通道里渲染目标不变时复用 Pass | 28 | **37.0** | **17.9** | 25.3 |

**营地：19.7 → 37 fps，现在受 GPU 限制。** 到遮挡查询那一行时，3D 选角页已从 24.7–27 fps 升到 39–40 fps。每一步的画面都与默认构建一致（同一场景截图对比）。

最后三行来自同进程 A/B：同一局里每 10 秒开、关一次所测的优化，关的那半分别是 34.1、35.2 和 36.1 fps。

## 发现

1. **计时作用域每帧读时钟约 95,000 次。**
   - simpleperf 显示渲染线程 19.3% 在 `__kernel_clock_gettime`，每次约 105 ns。
   - 分项统计（`NVN PERF parts`）改为每 8 帧计一帧。标记 `gfx-perf-sample=N` 可改；设 `1` 恢复每帧都计。
2. **每张彩色图像都带 `VK_IMAGE_CREATE_MUTABLE_FORMAT_BIT` 且不给格式列表，在 Adreno 上会关掉 UBWC。**
   - 去掉后 GPU 少 5.8 ms，CPU 少 3.8 ms（和 CPU 共用的内存流量变少）。
   - 开机、菜单、选角页、营地里，**从来没有一个视图用到别的格式**。Metal 后端为苹果显卡做了同样的选择：按它自己的统计，17,473 张贴图里需要的是 0 张。
   - 现在若遇到格式不同的视图，就像 `nvn_mtl.m` 的 `tex_upgrade_pfv` 那样就地升级：带上这个标志新建图像，逐 level、逐 layer 拷过去，旧图像和视图退役，描述符备忘作废。
   - `gfx-mutable-test=N` 每 N 张图像强制升级一次：营地一局升级 156 次，画面不变。
   - `gfx-mutable-images=1` 恢复原来的做法。
3. **每帧的每个渲染通道都新建再销毁帧缓冲。**
   - 这占渲染线程 5.3%；`vkResetCommandBuffer` 另占 3.6%。
   - 分配器约占 15%：Adreno 驱动在 `vkCmdDraw*` 里 `calloc`，加上引擎每次绘制的 vector 和 map 节点。
   - 现在缓存过的渲染通道的帧缓冲一直保留，直到其中第一张图像被销毁。每个槽有自己的命令池，整池重置。`create_pass` 复用自己的 vector。
4. **每帧 2,188 次绘制里有 558 次每次都重建描述符集**，每次约 21 µs，而备忘命中约 2.5 µs。备忘排除了 uniform 纹素缓冲。
   - 这 558 次绑的都是同一段约 1 MB 的纹素范围，游戏每帧都重写它。
   - 开 `gfx-texel-memo=1` 后每个槽保留一份常驻副本，内容变了才刷新，且只在本帧第一次读之前刷新。副本每次提交校验一次，而不是每次命中都校验；第一版每次命中都算哈希，每帧多花 37 ms。
   - 现在所有绘制都命中备忘，描述符部分从 9.6 ms 降到 5.4 ms。
5. **遮挡查询是 GPU 上最大的单项开销。**
   - 游戏第一次 `ResetCounter` 之后，每次绘制都有自己的精确遮挡查询，每帧约 2,200 个。
   - 一个都不录（诊断用 `gfx-no-occlusion`）时，GPU 从 36.8 ms 降到 26.1 ms，CPU 从 27.4 ms 降到 23.7 ms。
   - 计数仍须正确：在 Metal 上，报告值为 0 时游戏会把篝火和光源剔掉。
   - 仿照 Metal 按渲染通道计数，现在一个查询覆盖一段连续绘制。这段在通道结束、计数清零、报告（报告会结束通道）时结束，所以每次报告仍正好是自清零以来那些绘制的总和。每帧剩 48 个查询。
   - 3D 主通道从 19.1 ms 降到 12.9 ms，界面通道从 3.7 ms 降到 1.3 ms。
   - 在这些场景里，游戏每帧把通过采样数计数器清零 21 次，但这条路径上只报告时间戳（每帧 4 次）。
6. **主通道与分辨率（修遮挡查询之前）。** 把 3D 比例从 0.75 降到 0.6，主通道只从 19.6 ms 降到 16.8 ms。它的开销大部分不随像素数变化；逐次绘制的查询解释了这一点。
7. **存储写跟踪，现在走宿主的缺页钩子：**
   - 每帧拷约 22 KB 而不是 18.7 MB（三块 19.6 MB 缓冲里每帧 6–8 个脏页）；
   - 同进程 A/B（`gfx-ab-toggle` 配 `gfx-ab-target wtrack`：同一局里每 10 秒开、关交替，两半温度相同）：开 36.3 fps、关 35.2 fps，CPU 19.5 ms 对 20.7 ms，无不一致；
   - 在宿主掌管缺页处理时缺省开启（`gfx-no-wtrack` 或 `gfx-wtrack=0` 关掉）；没有这些钩子时仍是可选开启。
8. **管线查找每次绘制都重建可跨启动复用的键**，把布局和渲染通道的定义整段拷进键里，再在以 `std::string` 为键的 map 里查：约占渲染线程 7%。
   - 现在先查一级表：其键只在本进程内有效，用缓存条目指代那两份定义；没命中才建预热列表要用的完整键。
   - A/B：开 35.5 fps、关 34.1 fps，CPU 少 1.0 ms。
9. **每次绘制都完整跑一遍 `create_pass`：** 目标尺寸、帧缓冲规划、附件准备，以及视图、渲染通道、帧缓冲的查找。
   - 现在打开着的通道里、渲染目标状态逐字节相同的绘制直接用上一个 `Pass`。非绘制操作会结束通道，所以其间没有别的东西碰过这些附件；只刷新它们的写入标记。
   - 2,188 次绘制里有 2,140 次走这条路。A/B 中 CPU 从 19.7 ms 降到 17.9 ms，但帧率只从 36.1 到 37.0：一帧现在在等 GPU（呈现 2.7 ms）。
10. **几项小的：**
   - `++stats.draws` 每次绘制做一次顺序一致的原子加（占线程 2.7%，因为要等之前所有写入完成）；它只是诊断计数，改为宽松原子。
   - 每次提交的快照 map 复用节点。
   - 回读放进缓存内存（`gfx-readback-cached`）没有可测的差别。
   - 时间戳报告改为就地写入，不再结束通道并加两道完整屏障；A/B 中 GPU 没有差别（被它拆开的都是小通道）。
11. **做完以上之后的 3D 比例：** 用 0.6 代替 0.75 时，GPU 时间是 21.4 ms 而不是 25.3 ms，营地 39.5 fps。主通道从 12.9 ms 降到 10.6 ms，可见它仍有约一半不随像素数变化，多半是每次绘制的状态在每个分块里重放。比例是画质取舍，保持 0.75。

## 现在一帧的时间去向

- **一帧现在受 GPU 限制，约 27 ms：**
  - GPU：25.3 ms，其中 3D 主通道 12.9 ms；
  - CPU：提交 17.9 ms、呈现 2.7 ms（大部分在等 GPU），同一线程上游戏自己的代码约 6.5 ms。
- **每帧最大的几项 CPU：** 绘制准备 4.9 ms、描述符 4.8 ms、快照拷贝 4.5 ms、命令循环 3.8 ms、管线查找 1.5 ms。

## 新增标记（`files/dm/` 下的文件）

| 标记 | 没有它时 | 有它时 |
|---|---|---|
| `gfx-perf-sample` = N | 每 8 帧计一帧分项时间 | 每 N 帧；0 = 关 |
| `gfx-mutable-images` = 1 | 彩色图像不带 `MUTABLE_FORMAT` | 所有彩色图像都可换格式，同原来 |
| `gfx-mutable-test` = N | — | 测试用：每 N 张彩色图像强制就地升级 |
| `gfx-no-persistent-fb` | 帧缓冲跨帧保留 | 每槽帧缓冲，同原来 |
| `gfx-no-slot-pools` | 每槽一个命令池 | 共用命令池和 `vkResetCommandBuffer`，同原来 |
| `gfx-no-texel-memo` | 纹素常驻副本，描述符集进入备忘 | 每帧的纹素视图，同原来 |
| `gfx-query-per-draw` = 1 | 每段连续绘制一个遮挡查询 | 每次绘制一个，同原来 |
| `gfx-no-occlusion` = 1 | — | 诊断用：不录遮挡查询，报告值为 0 |
| `gfx-no-wtrack`（或 `gfx-wtrack` = 0） | 宿主掌管缺页处理时开写跟踪 | 关 |
| `gfx-readback-cached` = 1 | 回读在不带缓存的内存 | 回读放 CPU 缓存内存（无可测差别） |
| `gfx-heavy-timestamps` = 1 | 时间戳报告就地写入 | 结束通道并加完整屏障，同原来 |
| `gfx-ab-toggle` = N 配 `gfx-ab-target` | — | 同进程 A/B：每隔 N 秒把目标（`wtrack`、`pipefast`、`query`、`timestamps` 或 `passfast`）关掉一次 |
| `env` | — | 每行 `KEY=VALUE`，在 App 缺省值之前设进环境，例如 `DM_3D_SCALE=0.6` |

## 下一步

- **在更多场景跑纹素备忘**（别的幕、战斗、菜单）。它现在缺省开启，`gfx-no-texel-memo` 可关掉。
- **让游戏自己约 6.5 ms 的代码与翻译重叠。** 这要审计安卓上一直关着的异步翻译路径：游戏线程与翻译线程之间的对象生命周期。
- **管线查找：** 每次绘制都从完整的创建信息重建键（2.4 ms）。
- **GPU：** 3D 主通道（12.9 ms）现在是最大的单项；一帧已接近受 GPU 限制。
